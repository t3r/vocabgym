# Development & Deployment Workflow

## Project Context

VocabTrainer is a serverless web application for 9th grade German Gymnasium students learning French vocabulary. The application extracts vocabulary from scanned workbook images using AWS services and provides typing-based practice sessions.

**Technology Stack:**
- Frontend: Vue 3 (Composition API), Tailwind CSS, Vite
- Backend: AWS Lambda (Python 3.11+), API Gateway
- Database: DynamoDB
- Storage: S3
- CDN: CloudFront
- Authentication: AWS Cognito with OAuth2 flow
- OCR/AI: AWS Textract → Amazon Bedrock (Nova Pro, `eu.amazon.nova-pro-v1:0`)
- Infrastructure: AWS SAM (template.yaml in `backend/`)
- Region: eu-central-1

## Development Environment Setup

- Node.js 18+ and npm
- Python 3.11+

## Git Workflow

### Branch Strategy

This is a small solo project — all work is done directly on `main`:

```bash
git add <files>
git commit -m "feat: add vocabulary extraction review interface"
git push origin main
```

### Commit Convention

Use conventional commits:
- `feat:` — new feature
- `fix:` — bug fix
- `docs:` — documentation changes
- `style:` — formatting, no logic changes
- `refactor:` — code restructuring
- `test:` — adding tests
- `chore:` — maintenance tasks

Example: `feat: add multi-language support for vocab sets`

### Pre-Commit Hook

The project uses [betterleaks](https://github.com/betterleaks/betterleaks) v1.8.1 to prevent accidentally committing secrets. Configured in `.pre-commit-config.yaml`:

```yaml
repos:
  - repo: https://github.com/betterleaks/betterleaks
    rev: v1.8.1
    hooks:
      - id: betterleaks
```

Install hooks after cloning:
```bash
pre-commit install
```

## Deployment

### How to Deploy

All deployment is manual via the `deploy.sh` script:

```bash
./deploy.sh dev     # Deploy to dev environment
./deploy.sh prod    # Deploy to prod environment
```

**Allowed environments:** `dev`, `prod` (defined in `template.yaml` `AllowedValues`).

**What `deploy.sh` does:**
1. Builds backend with `sam build --use-container`
2. Deploys CloudFormation stack `vocabtrainer-{stage}` to eu-central-1
3. Reads stack outputs (API URL, Cognito IDs, S3 bucket, CloudFront distribution)
4. Writes `.env.production.local` with resolved values
5. Builds frontend with `npm run build` (uses `npx vite build` under the hood)
6. Syncs `dist/` to the frontend S3 bucket
7. Invalidates CloudFront cache

### Stack Naming

Stacks are named `vocabtrainer-{stage}`:
- `vocabtrainer-dev`
- `vocabtrainer-prod`

### Backend Build

```bash
cd backend
sam build --use-container
```

**Known issue:** The PracticeHandler function uses `python-Levenshtein`, which requires a C extension compiled for x86_64/Linux. Building with `--use-container` handles this. If the container build fails for this dependency, the workaround is to use a pre-built wheel or pin to a version with published x86_64 wheels.

### Frontend Build

```bash
cd frontend
npx vite build     # Output in dist/
```

### SAM Configuration

The `backend/samconfig.toml` has profiles for both environments:

- `[default.*]` — dev environment (stack: `vocabtrainer-dev`)
- `[prod.*]` — prod environment (stack: `vocabtrainer-prod`)

Region is eu-central-1 for all profiles.

### CI/CD

The project uses GitHub Actions for automated testing and deployment:

| Trigger | Workflow | Action |
|---------|----------|--------|
| Pull Request → `main` | `test.yml` | Run backend + frontend tests (mandatory) |
| Push → `main` | `deploy-dev.yml` | Tests + deploy to dev environment |
| GitHub Release (tag) | `deploy-prod.yml` | Tests + deploy to prod environment |

Workflows use OIDC (no long-lived AWS credentials). Each environment (`dev`, `prod`) in GitHub has its own secrets:
- `AWS_DEPLOY_ROLE_ARN` — IAM role for OIDC
- `CERTIFICATE_ARN` — ACM certificate ARN
- `HOSTED_ZONE_ID` — Route 53 hosted zone ID

> **Deploy-role note:** The async extraction stack adds SQS resources
> (`ExtractionQueue`, `ExtractionDLQ`) and an SQS→Lambda event source mapping.
> The OIDC deploy role must allow `sqs:CreateQueue`, `sqs:DeleteQueue`,
> `sqs:GetQueueAttributes`, `sqs:SetQueueAttributes`, `sqs:TagQueue` and
> `lambda:CreateEventSourceMapping`/`Update`/`Delete` (usually covered by the
> broad CloudFormation deploy policy; verify on first deploy of this change).

**Prod release:**
```bash
git tag v1.0.0
git push origin v1.0.0
# Then on GitHub: Releases → Create release from tag
```

### Custom Domain

The production frontend is served at **vocab.gym.t3r.de** via CloudFront + Route 53 + ACM (certificate in us-east-1). To enable custom domain support during deployment, create `backend/.env.deploy`:

```bash
CERTIFICATE_ARN=arn:aws:acm:us-east-1:...:certificate/xxx
HOSTED_ZONE_ID=Z0XXXXXXXXX
```

`deploy.sh` reads this file and passes the values as CloudFormation parameters. Without this file, deployment works but uses the default CloudFront domain.

### Post-Deployment Verification

After deploying:
1. Check the output URLs printed by `deploy.sh`
2. Open the frontend URL and verify the app loads
3. Test Cognito login flow
4. Upload a test image and verify extraction
5. Run a practice session

### Rollback

**Backend rollback:**
```bash
# Check recent stack events
aws cloudformation describe-stack-events \
  --stack-name vocabtrainer-dev --region eu-central-1

# Redeploy a previous commit
git checkout <previous-commit>
./deploy.sh dev
```

**Frontend-only rollback:**
```bash
git checkout <previous-commit>
cd frontend
npx vite build
aws s3 sync dist/ s3://<frontend-bucket> --delete --region eu-central-1
aws cloudfront create-invalidation --distribution-id <ID> --paths "/*"
```

## Database Migrations

Since DynamoDB is schema-less, "migrations" are primarily about adding new tables/GSIs or backfilling data.

Migration scripts live in the `scripts/` directory:

```
scripts/
└── migrate_to_multilang.py    # Adds language fields to existing vocab items
```

**Process:**
1. Update `template.yaml` if adding new tables or GSIs
2. Deploy infrastructure changes: `./deploy.sh dev`
3. Write migration script in `scripts/`
4. Run against dev first:
   ```bash
   cd scripts
   python migrate_to_multilang.py --stage dev
   ```
5. Verify data in dev, then run against prod

## Monitoring & Logging

### CloudWatch

**Log Groups:** `/aws/lambda/vocabtrainer-{env}-{function-name}`
- Retention: 7 days (dev), 90 days (prod)
- Lambda functions use AWS Lambda Powertools for structured logging

**Key Metrics:**
- Lambda invocation count, duration, errors
- API Gateway 4xx and 5xx errors
- DynamoDB read/write capacity usage

**Alarms (configured in template.yaml):**
- Lambda error rate > 5%
- API Gateway 5xx rate > 1%
- DynamoDB throttled requests > 0

### Structured Logging

All Lambda functions follow this pattern:

```python
from aws_lambda_powertools import Logger, Tracer, Metrics
from aws_lambda_powertools.metrics import MetricUnit

logger = Logger(service="vocab-extraction")
tracer = Tracer(service="vocab-extraction")
metrics = Metrics(namespace="VocabTrainer", service="vocab-extraction")

@tracer.capture_lambda_handler
@metrics.log_metrics(capture_cold_start_metric=True)
def lambda_handler(event, context):
    logger.info("Processing extraction", extra={"vocabSetId": vocab_set_id})
```

**PII rules:** Never log email addresses or passwords. Log Cognito user IDs only.

### Backup & Disaster Recovery

All 9 DynamoDB tables have Point-in-Time Recovery (PITR) enabled. AWS Backup is configured with tag-based selection:

- **Dev:** Daily backups, 7-day retention
- **Prod:** Daily backups (35-day retention) + weekly backups (90-day retention)

A prod-only SSM Automation restore-test runbook runs weekly (PITR) and monthly (AWS Backup source) to verify recoverability. An SNS topic + EventBridge rule alerts on runbook failures.

## Security

### Authentication & Authorization

- All API endpoints require Cognito JWT token (except health checks)
- Token expiration: access token 1 hour, refresh token 30 days
- Users can only access their own data (enforced in Lambda logic)
- Presigned S3 URLs with short expiration for image uploads

### Data Protection

- DynamoDB encryption at rest (AWS managed keys)
- S3 encryption (SSE-S3)
- HTTPS only (enforced via CloudFront and API Gateway)
- Extraction prompts stored in SSM Parameter Store (changeable without redeploy)
- betterleaks pre-commit hook prevents committing secrets

### Input Validation

- API Gateway request validators reject invalid payloads before Lambda
- Lambda functions validate with Pydantic models
- File uploads: max 10MB, allowed types: JPG, PNG, HEIC
- Rate limiting via API Gateway usage plans

## Cost Optimization

### AWS Cost Controls

## Troubleshooting

### Common Issues

**Lambda timeout during extraction:**
- Extraction handler has 5-minute timeout
- If Textract is slow, check image size (resize if > 5MB)
- Bedrock (Nova Pro) handles the extraction; verify model access in eu-central-1

**Cognito authentication failing:**
- Verify callback URLs in Cognito match the environment
- Check JWT token expiration
- Verify CORS on API Gateway

**DynamoDB throttling:**
- All tables use on-demand billing — should not occur
- Check for hot partition keys if it does

**S3 upload failing from frontend:**
- Check presigned URL not expired (5 min expiry)
- Verify CORS configuration on images bucket
- Confirm file size under 10MB limit

**CloudFront serving stale content:**
- `deploy.sh` auto-invalidates; if needed manually:
  ```bash
  aws cloudfront create-invalidation --distribution-id <ID> --paths "/*"
  ```

**sam build fails for PracticeHandler (python-Levenshtein):**
- Use `--use-container` flag (deploy.sh does this)
- If container build fails, try pinning `python-Levenshtein==0.25.1` or using `rapidfuzz` as alternative

### Debug Checklist

1. Check CloudWatch logs for the relevant Lambda function
2. Verify IAM permissions on Lambda execution role
3. Test API endpoint with curl and a valid JWT
4. Check DynamoDB item exists with correct key structure
5. Verify S3 object accessible with correct key path
6. Review recent `git log` for related changes
